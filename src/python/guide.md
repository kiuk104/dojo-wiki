## 프로그램 두 개가 같은 파일을 고칠 때 — 파일 잠금 {#cross-process-file-lock}

> 🏷️ `python` `잠금` `lock` `동시 작업` · 📅 2026-11-14

**한 줄 요약:** 같은 프로그램 안의 일꾼끼리는 `threading.Lock` 으로 줄을 세우지만, **서로 다른 프로그램**끼리는 그 잠금이 안 보여요. 그때는 **파일 하나를 '열쇠'로** 써서 운영체제에게 잠가 달라고 해요.

### 문제 / 상황
Fokus Podcast 앱(서버)은 피드 목록 파일(`external.json`)을 고칠 때 `threading.RLock()` 으로 "한 번에 하나씩" 을 지켜 왔어요.
그런데 옛 에피소드에 핵심어를 채우는 **스크립트**(`scripts/backfill_keywords.py`)를 따로 돌리게 됐어요. 스크립트도 같은 파일을 고쳐요.
- 앱의 잠금은 **앱 프로그램 안에만** 있어요. 스크립트는 다른 프로그램이라 그 잠금을 몰라요.
- 둘이 동시에 "읽고 → 고치고 → 저장" 하면, 늦게 저장한 쪽이 먼저 저장한 쪽의 내용을 **덮어써서 지워요.**

### 해결
파일 하나(`outputs/_feed.lock`)를 열쇠로 정하고, 고치기 전에 운영체제에게 "이 파일 잠가 줘" 라고 해요. 이미 누가 잠갔으면 기다리거나 포기해요.
```python
import msvcrt                      # 윈도우 (맥·리눅스는 fcntl.flock)

f = open(LOCK_PATH, "a+b")
try:
    msvcrt.locking(f.fileno(), msvcrt.LK_NBLCK, 1)   # NB = 기다리지 말고 바로 결과
    잡음 = True
except OSError:
    잡음 = False                    # 다른 프로그램이 잡고 있음
```
이걸 `with` 로 쓰게 감싸 두면 앱과 스크립트가 똑같이 써요:
```python
with feed_lock.hold("핵심어 채우기 스크립트"):   # 못 잡으면 "…가 피드를 고치는 중이에요"
    피드_고치기()
```
- 앱 쪽: 게시·내리기·피드 반영·📖 읽어주기가 모두 이 잠금을 잡아요. 스크립트가 도는 중이면 안내를 띄우고 멈춰요.
- 스크립트 쪽: 시작 전에 앱에 "지금 도는 작업 있어?" 를 물어보고(`/api/publish/status`), 끝날 때까지 잠금을 쥐고 있어요.
- 누가 잡았는지는 옆 파일(`_feed.lock.json`)에 이름을 적어 두어 안내 문구에 써요.

### 왜 그런가
- 3D 비유: 팀 작업에서 같은 `.blend` 파일을 두 사람이 동시에 열고 저장하면, 나중에 저장한 사람 것만 남죠. 그래서 **체크아웃(잠금)** 하는 에셋 관리 툴(Perforce 등)을 써요. 파일 잠금이 바로 그 체크아웃이에요.
- `threading.Lock` 은 **한 프로그램 안의 메모리**에 있는 깃발이라, 다른 프로그램은 볼 수 없어요. 파일 잠금은 **운영체제**가 관리해서 모든 프로그램이 같이 봐요.
- '파일이 있으면 잠긴 것' 처럼 파일을 만들고 지우는 방식도 있지만, 프로그램이 도중에 죽으면 파일이 남아 **영원히 잠긴** 상태가 돼요. 운영체제 잠금은 프로그램이 죽으면 **저절로 풀려요.**
- 같은 프로그램 안에서 겹쳐 잡는 경우(게시 안에서 또 게시를 부르는 등)는 몇 겹인지 세어서, 맨 바깥이 끝날 때만 풀어요.

> ⚠️ 주의 잠금을 **새로 만든 코드**만 잠금을 지켜요. 이미 켜져 있던 앱은 옛 코드라 모르니까, 스크립트를 돌리기 전에 앱을 **다시 시작**해야 해요. 그래서 스크립트가 "잠금을 아는 버전인지" 먼저 확인하고, 아니면 멈춰요.

## 오류는 메시지 글자 말고 상태 코드로 판단하기 {#status-code-not-message}

> 🏷️ `python` `http` `GitHub API` `재시도` · 📅 2026-11-14

**한 줄 요약:** "다시 해 볼 오류인지" 는 **숫자(상태 코드)** 로 판단한다. 오류 **문장**은 회사가 언제든 바꿀 수 있어서, 문장 속 단어로 판단하면 어느 날 갑자기 안 맞는다.

### 문제 / 상황
Fokus Podcast 는 GitHub 의 `external.json` 을 고칠 때, 그 사이 다른 쪽이 먼저 고쳤으면 GitHub 가 **409(충돌)** 를 줘요. 그러면 최신본을 다시 읽어 다시 저장하게 짜여 있었어요. 그런데 검사가 이랬어요:
```python
if r.status_code in (409, 422) and ("does not match" in r.text or "sha" in r.text):
    다시_시도()
```
옛 에피소드 23개의 자막을 연달아 올리다가 하나가 실패했어요. GitHub 가 보낸 문장이 이렇게 **바뀌어** 있었거든요:
`"is at 7a5ae5d… but expected bde0a43…"` → "does not match" 도 "sha" 도 없음 → 다시 해 보지도 않고 포기.

### 해결
409 는 뜻이 하나(버전 충돌)라서 **숫자만 보고** 다시 해요. 422 는 여러 뜻이라 그때만 내용을 확인해요.
```python
if attempt < 5 and (r.status_code == 409 or (r.status_code == 422 and "sha" in r.text)):
    time.sleep(1.5 * (attempt + 1))   # 잠깐 기다렸다가
    latest, sha = 다시_읽기()           # 최신본 위에
    text = rebuild(latest)             # 내 변경을 다시 얹어서 저장
```
테스트에도 **실제로 받은 문장**을 그대로 넣어, 옛 문장과 새 문장 둘 다 다시 시도하는지 확인해요.

### 왜 그런가
- 3D 비유: 파일 형식이 "버전 번호" 로 호환을 알려 주는 것과 같아요. 렌더러가 에러 창의 **글자**를 읽고 판단하면 번역판 블렌더에서는 안 맞지만, **에러 코드**는 그대로죠.
- 상태 코드는 약속(표준)이고, 메시지는 사람에게 보여 주려는 설명이에요. 설명은 다듬어지고 바뀌어요.
- 실패해도 괜찮게 만든 덕에(하나 실패해도 나머지 계속, 다시 돌리면 남은 것만) 고친 뒤 한 번 더 돌려서 끝났어요.

### 관련
- 프로그램 두 개가 같은 파일을 고칠 때 — 파일 잠금

## 어림 공식은 실제 데이터로 맞추기 (최소제곱) {#fit-estimate-from-data}

> 🏷️ `python` `numpy` `어림` `데이터` · 📅 2026-11-15

**한 줄 요약:** "문장 하나에 몇 초" 처럼 숫자 하나로 어림하면 2배씩 틀릴 수 있다. 이미 만든 결과물(실제 길이)을 모아 **numpy 의 최소제곱(lstsq)** 으로 공식의 계수를 맞추면 오차를 몇 %로 줄일 수 있다.

### 문제 / 상황
Fokus Podcast 가 긴 글을 "예상 길이가 45분을 넘으면 나누기" 로 하려면 MP3 를 만들기 **전에** 길이를 알아야 해요.
처음엔 "문장당 34초(중간값)" 를 생각했는데, 실제 에피소드를 보니 문장당 **25초 ~ 51초**로 두 배 차이 — 문장 길이와 반복 횟수가 달라서예요.

### 해결
길이를 만드는 재료를 나눠서 각각 몇 초인지 **실제 에피소드 24개**로 맞췄어요:
```python
import numpy as np
X, Y = [], []
for ep in 에피소드들:
    X.append([독일어글자 * (1 + 반복), 한국어글자, 구간수])   # 재료
    Y.append(실제_길이_초)                                   # 정답
coef, *_ = np.linalg.lstsq(np.array(X, float), np.array(Y, float), rcond=None)
# coef = [0.069, 0.129, 1.75]  → 독일어 한 글자 0.069초, 한국어 0.129초, 구간마다 무음 1.75초
```
그다음 **얼마나 맞는지 꼭 확인**: 평균 오차 6%, 가장 많이 틀린 것 13%. 2시간 12분짜리는 128분으로 어림.

### 왜 그런가
- 최소제곱 = "모든 에피소드에서 (어림 − 실제)² 의 합이 가장 작아지는 계수" 를 계산으로 찾는 방법이에요.
- 3D 비유: 스캔한 점들에 평면을 맞추는(Fit plane) 것과 같아요. 점 하나에 맞추면 기울어지지만, 점이 많으면 가장 잘 맞는 평면이 하나로 정해지죠.
- 재료를 나눈 게 중요해요. 독일어는 반복 횟수만큼 여러 번 읽히고, 한국어는 한 번, 무음은 구간마다 — 성격이 다른 것을 한 숫자로 뭉치면 틀려요.

> 💡 꿀팁 맞춘 계수 옆에 **언제·무엇으로 맞췄는지**와 오차를 주석으로 남겨 두세요. 목소리나 간격 설정이 바뀌면 다시 맞춰야 하니까요.

> ⚠️ 주의 같은 날 알게 된 것: 캐시(한 번 만든 음성을 다시 쓰는 저장소)는 **설정까지 포함한 이름(키)** 으로 찾아요. 한국어 발음 지시를 추가한 뒤로는 키가 달라져서, 그 전에 만든 한국어 음성이 캐시에 그대로 있어도 "없다" 고 판단해요. 캐시 키에 들어가는 값을 바꿀 땐 옛 캐시를 못 쓰게 된다는 걸 기억하기.
